Rebase the reviewed downstream commits on `alpha` onto the latest `upstream/latest-alpha-cli`, preserving relevant downstream functionality and validating the resulting branch.

- Start from a clean `alpha` branch. Before rebasing, create a new, uniquely named backup, call it `alpha.rebasing-onto-*` (where `*` is the version of the current `upstream/latest-alpha-cli`); Stick to rebasing this version, and do not allow the rebase to change target (even if `upstream/latest-alpha-cli` changes during the rebase).
- Rebase `alpha` onto it, organizing the replay to minimize unnecessary shifts between unrelated areas of work. Record meaningful skips, conflict resolutions, and deviations.
- Keep progress in a dedicated `REBASE-PROGRESS.md` file, updating it as the rebase proceeds with the pinned target, replay/conflict decisions, follow-up fixes, and validation results or blockers.
- Once the first rebase succeeds, and before running tests, create and switch to a working branch named for the pinned upstream target, such as `rebasing-v0.163.0-alpha.11` when `upstream/latest-alpha-cli` points to `rust-v0.163.0-alpha11`. Push this branch to GitHub and keep it updated with follow-up fixup commits as validation finds issues.
- Only after the rebase is complete, validate the resulting branch: run the relevant tests, build locally as a debug build (`build_codex.sh --debug`), ensure the Flip7 and Pi 3 builds/installations are release builds (`build_codex.sh --release --install flip7,pi3`), and verify that `codex exec --bare-prompt 'say hi'` runs on flip7,pi3 with under-20 token usage. `build_codex.sh --restart-if-idle` is an optional install argument; do not pass it during rebase testing, and do not issue `codex app-server daemon restart-if-idle` as part of the native build.
- If validation fails, use the failure and commit history to identify the most likely offending change without defaulting to a slow bisect. Edit that commit, validate the fix, continue the rebase, and rerun validation. Repeat until the final rebase passes, or report precisely what remains blocked. Refer to DOWNSTREAM.md to seek clarification on where we intend to deviate from the `upstream` version, and document every code change we make explaining which entry in DOWNSTREAM.md it relates to.
- Do not squash or rewrite git history while ensuring the relevant tests and fixes work. Squashing is a separate task not covered by this goal document.
