Rebase the reviewed downstream commits on `alpha` onto the latest `upstream/latest-alpha-cli`, preserving relevant downstream functionality and validating the resulting branch.

- Start from a clean `alpha` branch. Before rebasing, create a new, uniquely named backup, call it `alpha.rebasing-onto-*` (where `*` is the version of the current `upstream/latest-alpha-cli`); Stick to rebasing this version, and do not allow the rebase to change target (even if `upstream/latest-alpha-cli` changes during the rebase).
- Rebase `alpha` onto it, organizing the replay to minimize unnecessary shifts between unrelated areas of work. Record meaningful skips, conflict resolutions, and deviations.
- Maintain two dedicated records throughout the goal: `REBASE-TODO.md` is the authoritative checklist of remaining work and gates, and should shrink as items are completed until it contains only a one-line completion marker (or is removed); `REBASE-DONE.md` is the audit trail of completed work, decisions, and validation evidence. Keep both in the repository. Commit changes to either file separately, with no unrelated changes in the same commit. Update both as work proceeds, and prune or empty them as soon as their content stops being relevant. Never use the ambiguous former `REBASE-PROGRESS.md` name.
- Once the first rebase succeeds, and before running tests, create and switch to a working branch named for the pinned upstream target, such as `rebasing-v0.163.0-alpha.11` when `upstream/latest-alpha-cli` points to `rust-v0.163.0-alpha11`. Push this branch to GitHub and keep it updated with follow-up fixup commits as validation finds issues.
- Before each test or build validation run, commit completed source fixes as `fixup!` commits to their owning commits, so each run starts from a clean, identifiable source revision. When fixing more than one commit that touched the same file, stage and commit the file's current fix as a `fixup!` to its owning commit before editing that file for a fixup to a different commit. Keep changes for different owners separate so the same file cannot accidentally accumulate unrelated fixups.
- Only after the rebase is complete, validate the resulting branch: run the relevant tests, then build and install the native host, Flip7, and Pi 3 in one command (`build_codex.sh --install localhost,flip7,pi3`). Installs default to the ordinary `dev` profile for localhost and the unoptimized, stripped `dev-small` profile for SSH targets. A profile suffix overrides the target's default, for example `localhost:dev` or `pi3:release`; `localhost` performs the same local native build and install as omitting `--install`, and can be combined with SSH targets in one command. Build speed is the priority: preserve and reuse existing target artifacts, use the configured sccache with `CARGO_INCREMENTAL=0`, and do not clean target directories. `dev-small` inherits the unoptimized dev profile (`opt-level = 0`); it omits debug information and strips symbols. Verify that `codex exec --bare-prompt 'say hi'` runs on both devices with under-20 token usage. After all tests and device checks pass, make the final release builds and installs for Flip7 and Pi 3 while keeping localhost on `dev` (`build_codex.sh --release --install localhost:dev,flip7,pi3 --restart-if-idle`). The restart flag applies after a local or remote binary changes and requests an idle app-server restart; do not pass it during rebase testing, and do not issue `codex app-server daemon restart-if-idle` as part of the native build.
- `build_codex.sh` records per-stage user CPU, system CPU, total CPU, and elapsed seconds as JSONL in the external build tree at `build/codex-build-timings.jsonl`. Retain this record when comparing profile or device build costs.
- After installation, run `codex-pairing-code` on both flip7 and pi3 and verify that it successfully prints a pairing code.
- If validation fails, use the failure and commit history to identify the most likely offending change without defaulting to a slow bisect. Edit that commit, validate the fix, continue the rebase, and rerun validation. Repeat until the final rebase passes, or report precisely what remains blocked. Refer to DOWNSTREAM.md to seek clarification on where we intend to deviate from the `upstream` version, and document every code change we make explaining which entry in DOWNSTREAM.md it relates to.
- Do not squash or rewrite git history while ensuring the relevant tests and fixes work. Squashing is a separate task not covered by this goal document.
