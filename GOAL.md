Prepare `alpha` for a focused, understandable rebase onto `upstream/latest-alpha-cli`, then complete and validate that rebase.
Before each history-rearrangement exercise, verify that `alpha` is clean and create a new, uniquely named `alpha.before-rearrange-*` branch at its exact starting commit. Never overwrite an existing checkpoint. Record both the branch’s commit and tree hash; after rearranging, verify that the resulting tree hash matches the checkpoint. If it does not, investigate and correct the drift before proceeding.
Inspect downstream commits since the merge-base and classify changes by the feature, API, or behavior that owns them—not only by which file a later repair touches.
- Check every `fixup!` commit to confirm its target is the right downstream commit. Retarget it if needed, and autosquash valid fixups.
- When a change repairs, completes, or adapts something introduced by a downstream commit, make it an actual `fixup!` targeting that commit. Do not leave it as a regular “compat” or similarly named commit merely because its code is in a different file.
- If ownership is uncertain, investigate the relevant symbol or behavior and its history, identify plausible downstream owners, and resolve the classification consciously before committing. If no meaningful downstream owner exists, keep the change as a separate, clearly scoped commit and record why it is not a fixup.
- Split unrelated changes out of mixed commits and place them beside their logical owners, using fixups where appropriate. Prefer coherent, manageable rebase units, especially for files that also exist upstream. Historical changes to files absent upstream may remain grouped when that is clearer.
- Reduce repeated downstream edits to the same file: where practical, consolidate related changes so each file is touched in only one coherent downstream commit or fixup cluster. Keep repeated touches when independent features, dependencies, or other practical constraints make consolidation clearer; record why.
- Retain downstream functionality that remains relevant after upstream’s evolution. Remove or adapt changes only when they are obsolete, superseded, or no longer make sense; document material omissions and their reasons.
- Preserve the tree represented by the before-rearrange checkpoint. If desirable upstream-compatibility improvements would cause a mismatch, do not silently discard them: isolate the checkpoint-preserving conformity in a clearly labelled commit that explicitly says it is not intended to remain in the final upstream rebase, and document the trade-off.
- Before rebasing, create a new, uniquely named backup of the reviewed, rearranged alpha; do not overwrite existing checkpoints. Verify the backup and branch point to the intended commits and that the working tree is clean.
- Rebase `alpha` onto the current `upstream/latest-alpha-cli`, organizing the replay to minimize unnecessary shifts between unrelated areas of work. Record meaningful skips, conflict resolutions, and deviations.
- Build (locally but also ensure `build_codex.sh --release --install flip7` works and that a `codex exec --bare-prompt 'say hi'` runs on flip7 with under-20 token usage) and run the relevant tests after the rebase. If validation fails, use the failure and commit history to identify the most likely offending change without defaulting to a slow bisect. Edit that commit, validate the fix, continue the rebase, and rerun validation. Repeat as needed until the final rebase passes, or report precisely what remains blocked.
- After every history rewrite, verify the resulting tree against its safety checkpoint and confirm that fixups are attached to their intended downstream commits. Keep durable notes of the decisions, checkpoints, test results, and unresolved issues.
