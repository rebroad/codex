Rearrange the downstream history into a focused, understandable series. Keep the merge-base locked at the start of each operation as described below; do not rebase onto or advance to a newer upstream commit during this goal.

At the very start of each rearrangement operation, inspect the available `upstream/main` and `upstream/master` refs and determine which is the applicable upstream line for the downstream branch. Derive the operation's merge-base by comparing the downstream branch with that ref using Git's merge-base calculation. If both refs are available, confirm they identify the same applicable upstream history and merge-base; if the correct ref or base is ambiguous, stop before rearranging and investigate. Lock the resulting full commit SHA, and record the chosen upstream ref and SHA in `REARRANGE-TODO.md` and `REARRANGE-DONE.md` before changing any refs or commits. Use this locked commit as the sole lower boundary for the downstream range throughout the operation; do not recompute or replace it from a moving branch, a newer upstream commit, or the downstream branch ancestry. Limit ownership analysis, fixup validation/retargeting, and autosquashing to commits strictly after this base; commits at or before it, are upstream history and cannot be downstream owners or squash/fixup targets.

Scope clarification: this exercise is exclusively about rearranging Git history. Running tests or builds is prohibited for the entire goal; discovering test failures would create errors we cannot address without violating the required source-tree and checkpoint-tree invariants. Do not make source-code or test-coverage changes. During the rearrangement, note bugs observed in the code in `BUGS.md`, including enough context to identify each issue. Create `BUGS.md` if it does not already exist. Verify rearrangement only through Git history, range-diffs, clean-tree checks, the fixed merge-base, and exact equality of the source tree with the checkpoint. For this comparison, exclude `BUGS.md`, `REARRANGE-DONE.md`, and `REARRANGE-TODO.md` from both trees; the remaining source tree must match the checkpoint exactly. These records may differ from their checkpoint versions and must remain in the repository while the goal is active.

`REARRANGE-TODO.md` and `REARRANGE-DONE.md` are local working records and must not be tracked in Git. If either is already tracked, remove it from the index while preserving the local file. Keep the files available in the working tree during the goal; do not commit their contents. `BUGS.md` remains a tracked project record. For non-bug observations about areas that would benefit from refactoring, use a separate `REFACTOR.md`; record concise context and rationale there rather than classifying the suggestion as a bug.

Before each history-rearrangement exercise, verify that the downstream branch is clean and create a new, uniquely named `before-rearrange-*` checkpoint branch at its exact starting commit. Never overwrite an existing checkpoint. Record the downstream branch’s commit and tree hash. Verify final tree equality with the checkpoint using the record-file exclusions described above; investigate and correct any drift before proceeding.
Inspect downstream commits after the locked base and classify changes by the feature, API, or behavior that owns them—not only by which file a later repair touches.
- Check every `fixup!` commit to confirm its target is the right downstream commit. Retarget it if needed, and autosquash valid fixups.
- Autosquash fixups into their intended owner commits; do not combine distinct historical commits just because a fixup touches both or both affect the same file. If one fixup repairs changes with different owners, split it into separate fixups (or otherwise separate, clearly scoped commits) for those owners before autosquashing. Preserve separate commits for independent purposes, even when they touch the same file; the goal is to attach repairs to their owners, not to minimize the commit count.
- When a change repairs, completes, or adapts something introduced by a downstream commit, make it an actual `fixup!` targeting that commit. Do not leave it as a regular “compat” or similarly named commit merely because its code is in a different file.
- If ownership is uncertain, investigate the relevant symbol or behavior and its history, identify plausible downstream owners, and resolve the classification consciously before committing. If no meaningful downstream owner exists, keep the change as a separate, clearly scoped commit and record why it is not a fixup.
- Split unrelated changes out of mixed commits and place them beside their logical owners, using fixups where appropriate. Prefer coherent, manageable rebase units, especially for files that also exist upstream. Historical changes to files absent upstream may remain grouped when that is clearer.
- Reduce repeated downstream edits to the same file, not only commits explicitly named `fixup!`. Review the full downstream range for later commits that continue, repair, complete, or revise earlier changes in the same file, and consolidate related edits with their semantic owner. Aim for no more than one or two commits per independent feature or behavior touching any given file, where that preserves the distinct purposes of the historical commits. Do not merge independent features or behaviors merely to meet a file-touch count; keep their commits separate and record why additional touches are justified.
- Retain downstream functionality that remains relevant after upstream’s evolution. Remove or adapt changes only when they are obsolete, superseded, or no longer make sense; document material omissions and their reasons.
- Preserve the tree represented by the before-rearrange checkpoint. If desirable upstream-compatibility improvements would cause a mismatch, do not silently discard them: isolate the checkpoint-preserving conformity in a clearly labelled commit that explicitly says it is not intended to remain in the final upstream rebase, and document the trade-off.
- Finish with the downstream branch clean and fixups attached to their intended downstream commits. Keep durable notes of the decisions, checkpoints, and unresolved issues. The locked base and checkpoint-tree equality are verified as described above. The separate `GOAL-rebase.md` covers replaying this reviewed series onto the latest upstream CLI.
- Maintain two local, untracked records throughout the goal, and use them to track the current state of the work:
  - `REARRANGE-TODO.md` is the authoritative checklist of remaining work and gates. Keep it accurate as work proceeds, removing or revising completed and superseded items; when all work is complete, leave only a one-line completion marker or remove the file.
  - `REARRANGE-DONE.md` is a concise audit trail of completed phases, material decisions, checkpoints, and verification evidence. Update it when a phase or material decision is completed, but do not use it as a running transcript or append a separate entry for every small command, retry, or wording correction. Preserve evidence needed to understand or verify the rearrangement; prune detail that has become redundant or irrelevant.
  - Keep both files in the working tree while the goal is active, but never add or commit them. Their contents may evolve to reflect current progress.
